# Photo vault key foundation (Android only)

`migrateLegacyGalleryPhotos()` is an explicit action intended for the authenticated gallery, not an automatic mount step. It scans only direct regular `.jpg`/`.jpeg` children of the fixed private gallery, one at a time, caps each file at 64 MiB, and returns migrated/remaining/failed counts with a generic error code. Each original is removed only after authenticated ciphertext matches its bytes; interrupted runs retain originals and can resume. Existing encrypted photos and unrelated metadata are left alone. This is not a backup guarantee: verified migration replaces the original in place, so preserve any separate copy you need before choosing the action.
The migration and gallery-delete bridge share one process-wide mutation gate. Gallery screens rejoin an existing migration after remount instead of starting another one. Counts describe eligible JPEGs remaining at completion; a newly added JPEG is left for the next explicit run. A missing original is not counted as verified migration completion. The source inode and bytes are checked again before removal; exclusivity assumes cooperative app-owned mutations under this gate, not malicious code with arbitrary same-UID filesystem access. Ciphertext and its directory are synced before removal, then the directory is synced again after unlink.

## Share exports

`prepareEncryptedPhotoShare(filename)` authenticates one encrypted gallery leaf and writes a distinct JPEG under app cache `photo-vault-shares`; it never shares a private `.scv` view URI. Unhanded exports can be removed with `abandonOwnedShare(uri)`. Call `beginEncryptedPhotoShare(uri)` before platform handoff and `finishEncryptedPhotoShare(uri)` when the share promise settles. The lease avoids in-process cleanup while pending and sets a persisted one-hour expiry at settlement. Handed-off exports are not deleted on cancel/error because a receiver may still be reading them.

Cleanup runs at startup, foreground entry, before preparation, and every 15 minutes while the module lives. Persisted expiry survives process restart; only strict `share-<UUID>.jpg` names are eligible. This is best-effort cache retention, not secure erasure; Android may evict cache sooner, and recipients control copies. Expo Sharing grants chooser targets read access via its FileProvider.

## Native contract

- `initializeNewVault()` explicitly creates the stable alias `secret-camera.photo-vault.v1` using AndroidKeyStore AES-256 with GCM and no padding. It refuses an already-present alias; it never rotates it.
- `requireExistingKey()` retrieves only that alias. If missing or not a `SecretKey`, it throws a non-secret `IllegalStateException`; it does not create a key or substitute another one. A key invalidated or otherwise rejected by AndroidKeyStore/crypto operations must be surfaced to the caller; do not silently initialize a replacement because previously encrypted content would be unrecoverable.
- The Expo bridge methods return the nonsecret alias only. `SecretKey`/raw bytes remain native and `SecretKey.encoded` is not exportable. Hardware-backed storage depends on the device and is not guaranteed.

## Next consumer contract

The existing key adapter is used only through `requireExistingKey()` for codec operations; no codec operation initializes or rotates the alias. No photo integration, migration, backup, relock, biometric prompt, or iOS behavior is implemented here.

## Codec contract

- `encryptFile(inputPath, outputPath)` and `decryptFile(inputPath, outputPath)` are asynchronous native operations. Both paths must be absolute direct children of the app's private `filesDir`; JS callers must first resolve app-private paths (not pass arbitrary external filesystem paths). Existing output files are refused, never overwritten.
- The binary envelope is `SCPH` + version byte `0x01` + 12-byte fresh GCM nonce + AES-GCM ciphertext and 16-byte tag. The complete fixed header is authenticated as AAD. Decryption validates format/length and authenticates with `doFinal` before creating/publishing any plaintext file.
- Staging is in the destination directory, mode 0600, synced, and published by `renameat2(..., RENAME_NOREPLACE)` through the pinned directory descriptor. The implementation calls the kernel syscall directly rather than depending on bionic's API-30 libc wrapper, preserving the API-24 minimum. If the kernel/filesystem does not implement the syscall/flag or the process policy denies it, publication fails closed; there is no rename, hard-link, or check-then-rename fallback. A competing file or symlink therefore remains untouched.
- This JCA GCM implementation buffers input and authenticated output, so files are capped at 64 MiB (plus envelope overhead); it is not an unbounded streaming codec. Input is read on Expo's module queue using bounded reads. Encryption nonces are generated by AndroidKeyStore itself; the codec does not supply caller IVs. Each operation opens the app-private `filesDir` once with `O_NOFOLLOW` and performs input reads, staging and exclusive publication through that pinned directory descriptor, so parent-directory swaps during an operation cannot redirect I/O outside the private vault. The app-private root itself is a trusted platform context, not an adversarial boundary. No UI/capture/gallery/share/migration or app-photo wiring is included; the app still does not encrypt its photos.

From the repository root, after SDK 52 prebuild has generated `android/`, compile the module and instrumented tests with `cd android && ./gradlew :expo-photo-vault:compileDebugAndroidTestKotlin :expo-photo-vault:assembleDebugAndroidTest`. The actual autolinked Gradle project is `:expo-photo-vault` (confirmed by `./gradlew projects`). On an authorized Android device/emulator run `cd android && ./gradlew :expo-photo-vault:connectedDebugAndroidTest`. Instrumented tests use isolated synthetic aliases and synthetic bytes; they exercise AndroidKeyStore only when run on Android. A JVM/JCA test is not equivalent evidence.
